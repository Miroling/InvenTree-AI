# Cloud hosting and InvenTree credential boundaries

Verified against public primary documentation on **2026-09-05**. Research for [Research cloud hosting and InvenTree credential boundaries](https://github.com/Miroling/InvenTree-AI/issues/4). No private instance, VPS, or deployment server was accessed. No hosting or identity provider has been chosen, purchased, or provisioned.

## Finding

All three runtime approaches below are plausible for a remote MCP service. The decisive questions are who operates it, how it reaches InvenTree, and whether it serves one owner or unrelated customers. Public source distribution and operation of a shared service are separate decisions. A reusable repository can support separate owner deployments without becoming a multi-tenant SaaS.

Keep a portable HTTP container as a **candidate packaging baseline**, then select a documented deployment profile after those questions are answered. This is a recommendation, not an approved architecture. The comparison covers the MCP integration service; it does not propose migrating InvenTree itself.

## Transport state is different from durable identity state

Streamable HTTP permits either JSON responses or SSE and makes server-assigned session IDs optional. A session can end and require reinitialization; resuming an interrupted stream is optional. Therefore, a long-lived connection is not a durability guarantee. Prefer a stateless transport if the needed features permit it; otherwise decide how sessions and replay data survive routing and restart. [MCP transport specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

Separately inventory what the chosen authentication library/provider actually stores: client registrations where applicable, account-to-InvenTree mappings, refresh credentials where applicable, consent/revocation records, and signing keys. Some belong to the external identity provider; some may belong to this service. OAuth does not imply that all must be stored locally. **Any state this service needs across requests, redeploys, or token refresh must not depend on an ephemeral container filesystem.** Select the provider/storage adapter after the identity model; do not invent a custom OAuth server to fit a hosting choice.

Reviewable Change Plans and evidence of approval, if persisted, are application state too. A restarted or retried request must not silently apply an inventory write twice. Transport reinitialization does not itself resolve that product requirement.

## Two authentication boundaries

1. **Client to MCP service:** the client obtains authorization to call this service. Under MCP's HTTP authorization specification, the resource advertises authorization-server metadata, the flow uses PKCE, and tokens must be intended for this MCP resource. Registration may use pre-registration, client metadata documents, or dynamic registration depending on supported capabilities. An identity-provider compatibility check must establish the exact combination supported by both clients. [MCP authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)
2. **MCP service to InvenTree:** the service authenticates separately to the inventory API. InvenTree documents username/password and user-token access, recommends tokens, and uses the `Authorization: Token …` header. API actions are constrained by the authenticated user's permissions. [InvenTree API](https://docs.inventree.org/en/1.5.x/api/)

Never forward the MCP client's bearer token as the InvenTree credential. The MCP specification prohibits token passthrough and requires a separate upstream token where the server acts as an upstream OAuth client. This remains true if both systems happen to use the same identity provider. [MCP token requirements](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization#token-requirements)

Cloud Run's hosting guide demonstrates Google IAM/local-proxy or ID-token authentication. Those examples establish hosting viability, not browser ChatGPT OAuth compatibility. A browser-oriented deployment needs an ingress/authentication arrangement that the target client actually supports. [Cloud Run MCP authentication](https://docs.cloud.google.com/run/docs/host-mcp-servers#authenticate_mcp_clients_for_ai_agents)

### What InvenTree permissions can establish

InvenTree assigns permissions through groups and roles. Roles cover domains including parts, stock, BOM, builds, orders, and locations, with separate **view, add, change, and delete** permissions. Superuser bypasses these restrictions; staff enables sensitive administrative capabilities. A dedicated, non-staff, non-superuser integration account with selected role permissions is a viable candidate for one owner. Omitting delete permissions complements this project's no-automated-deletion policy, but does not replace tool-level restrictions or write approval. [User permissions](https://docs.inventree.org/en/stable/settings/permissions/)

The published user API schema includes token expiry and revocation fields. Do not interpret a reusable token as necessarily everlasting, or describe ordinary tokens as independently scoped OAuth grants. Confirm the supported token lifecycle against the eventual target version. [User API schema](https://docs.inventree.org/en/stable/api/schema/user/)

InvenTree 1.5 documentation also describes **experimental, explicitly enabled OAuth2/OIDC**, public clients with PKCE, application management, and scopes linked to roles. This is a possible upstream delegation route, not evidence that an existing instance is enabled or that it is a complete MCP-compatible authorization server. In particular, metadata, audience/resource behavior, client registration, and refresh/revocation compatibility still need verification before relying on it. [InvenTree OAuth/OIDC](https://docs.inventree.org/en/1.5.x/api/#oauth2-and-oidc)

Stock ownership documentation is not sufficient evidence of tenant isolation: it discusses UI restrictions and underlying role access. Do not infer general per-customer isolation from ownership labels. [Stock ownership](https://docs.inventree.org/en/stable/stock/owner/)

## Private MCP access variant

OpenAI's Secure MCP Tunnel can connect eligible ChatGPT developer-mode configurations to private MCP without a public MCP listener. The tunnel client must remain running within a network that reaches MCP, with a tunnel ID, runtime API key, and outbound HTTPS to OpenAI. Documented placements include VM services and Kubernetes, so this need not depend on an owner's laptop. It is an access path, not a hosting provider. Tunnel creation/use permissions, workspace/Platform organization association, and developer-mode access must be verified for the owner. OAuth discovery can traverse the tunnel; the authorization server is not automatically tunneled. [Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels)

Developer-mode connection supports selecting a tunnel. Public plugin submission/distribution requires stable public HTTPS instead. Public GitHub publication alone does not settle which distribution route is desired. Do not assume the ChatGPT tunnel also supplies the desired Codex connection; that needs its own client check. [Connect and test](https://developers.openai.com/plugins/deploy/connect-chatgpt)

An always-running tunnel process would need its own lifecycle analysis before being combined with a scale-to-zero service; that combination is not established by this research.

## Uploads and operational evidence

InvenTree's official Python interface supports native file uploads. This does not make a path on a user's computer readable by a remote MCP service. The product must choose how a client provides attachment content, enforce a maximum size and retention policy, and avoid exposing upstream credentials in file URLs. [Python interface](https://docs.inventree.org/en/latest/api/python/)

For Cloud Run, HTTP/1 requests are limited to 32 MiB; this specific limit does not apply to an HTTP/2 server. App/client limits still apply, and temporary files consume container memory. Render and owner-hosted upload limits must be established for the selected application/proxy configuration; this report makes no unlimited-upload claim. [Cloud Run quotas](https://docs.cloud.google.com/run/quotas), [filesystem](https://docs.cloud.google.com/run/docs/container-contract#file_system)

For all options, proposed logs should capture authenticated actor, approved plan identifier, tool/action, outcome, and correlation identifiers while excluding credentials and unnecessary inventory/attachment content. Managed logs do not automatically become a trustworthy inventory audit trail. Test this against synthetic inventory during later implementation.

## Conditional recommendation and next decisions

- **One owner, private InvenTree, willing host operator:** compare an owner-operated container close to InvenTree with public authenticated HTTPS or an eligible private tunnel. This minimizes the need for a separate route into the inventory network; operational ownership still matters.
- **One owner, reachable InvenTree, minimum infrastructure administration:** a paid Render web service is a credible first managed profile. Compare single-instance disk simplicity against an external database before committing to persistence.
- **Intermittent workload, acceptable cold starts, or existing Google Cloud network/services:** Cloud Run is credible with external required state and tested reconnection. It is not automatically simplest once private networking and identity dependencies are counted.
- **Unrelated customers in one shared service:** defer provider selection until tenant ownership, onboarding, per-user/upstream credential mapping, isolation, credential encryption/rotation, and offboarding are specified. A global InvenTree token would make every caller act as the same upstream user and is not a per-user authorization design.

The owner should resolve these questions next:

1. Is the first release a reusable one-owner deployment, a workspace deployment with several people, or a shared service for unrelated customers?
2. Is each caller represented by their own InvenTree identity, or may authorized callers share one dedicated integration identity?
3. Must InvenTree remain privately reachable, and who will operate any required network path? The actual instance version and network topology remain unknown; future inspection requires explicit permission.
4. Is manual/private browser connection sufficient, or is public plugin distribution part of the destination? Are the relevant ChatGPT/Codex account capabilities available?
5. Which runtime responsibilities, recurring budget, region, cold-start delay, attachment size, and outage/recovery expectations are acceptable?
6. Which maintained identity provider/library satisfies both clients and the selected mapping, and which durable records does that choice require?

Before treating a runtime as validated, a later authorized prototype should use synthetic data to exercise login and refresh, a streaming request, a container restart, reconnect to another instance where applicable, secret rotation, attachment limits, and approved-write retry behavior. These are proposed acceptance checks; no such deployment or private-system test was performed in this research.
